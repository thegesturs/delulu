title: Email lifecycle operations
description: Configure hosted transactional mail, lifecycle messaging, webhooks, and retention safeguards.
---

This runbook applies to the commercial hosted deployment. Clerk remains the sole sender for authentication, account-security, workspace-invitation, and role-change mail.

## Sending domains and secrets

1. Onboard the transactional sending domain in Cloudflare Email Service, publish its SPF, DKIM, and DMARC records, and bind `EMAIL` to the API Worker.
2. Set `CLOUDFLARE_EMAIL_FROM` and the `LOOPS_API_KEY` Worker secret. Never commit either value.
3. Configure the lifecycle sending domain in Loops and create event-triggered workflows for the events below.
4. Route replies to the support inbox. Every lifecycle message needs a one-click unsubscribe that sets `product_lifecycle_enabled=false`.

## Calendar webhook

Create one dedicated 15-minute retention event and one webhook using API version `2021-10-20`:

- Subscriber URL: `https://api.delulu.social/webhooks/cal`
- Triggers: booking created, rescheduled, and canceled only
- Custom payload template: disabled
- Secret: a new random value stored as `CAL_WEBHOOK_SECRET`

Set `CAL_RETENTION_EVENT_SLUG` to the configured event slug, deploy the API, and run the provider's ping test. The handler verifies `x-cal-signature-256` against the raw request body and resolves accounts only from opaque `cancellationReference` embed metadata.

## Billing webhook

Keep the hosted billing webhook at `/webhooks/dodo` and enable payment success/failure plus subscription active, updated, renewed, on-hold, plan-changed, canceled, failed, and expired events.

The production credential needs permission to update subscriptions, create wallet credits and checkout sessions, and open the customer portal. Authenticated checkout writes `billing_owner_user_id` into opaque provider metadata. Recurring events may fall back only to an already-linked provider customer ID, never a customer name or email.

Retries are safe because webhook claims, wallet credits, cancellation transitions, and queued messages are idempotent.

## Lifecycle workflows

| Event | Workflow and exit condition |
| --- | --- |
| `subscription.active` | Paid welcome; exit when a social account connects |
| `onboarding_incomplete` | Rescue at 24 hours, 3 days, and 7 days; exit on completion |
| `instagram_connected` | Education at 3 and 7 days only when no matching automation exists |
| `post_scheduled`, `post_published`, `automation_created` | Send once for each first-value milestone |
| `user_inactive` | Reactivation at 7, 14, and 30 days; exit on activity or cancellation |
| `payment_failed` | Recovery; exit on payment recovery or cancellation |
| `cancellation_scheduled` | At cancellation, then 7 and 30 days after term end |

Apply a global cap of two lifecycle messages per rolling seven days and a 24-hour quiet period after billing or security mail. Suppress lifecycle messages when the preference is disabled, cancellation is pending, or the account is deleted.

## Cancellation and deletion

Cancellation copy must explain that publishing and automations end at term end, data remains recoverable for 60 days, and permanent deletion follows subject to legal retention. Collect a reason and comment; eligibility checks must gate any retention credit.

Send recovery notices 30 and 7 days before deletion. The deletion worker revokes access and connection tokens before removing user data, then sends a transactional completion notice.
