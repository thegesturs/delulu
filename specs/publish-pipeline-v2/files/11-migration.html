11 — Migration

Phased zero-downtime rollout from current direct-write pipeline to job orchestration.

Phase overview

PhaseDurationRiskRollback
Phase 0 — Instrument3 daysNoneN/A
Phase 1 — Additive schema1 weekLowDrop tables
Phase 2 — Dual path1 weekMediumFeature flag off
Phase 3 — Cutover3 daysMediumFeature flag on old path
Phase 4 — Webhooks1 weekLowRevert DNS/URLs
Phase 5 — Cleanup3 daysLowN/A

Phase 0 — Instrument (3 days)

Goal: Baseline metrics before any code changes.

  • Add PostHog events: publish_job_created, publish_attempt_started, publish_attempt_failed
  • Instrument existing updatePostPublishStatus with attempt logging (console structured logs)
  • Document current failure rates per platform from CloudWatch
  • Ship this spec folder
Gate

Phase 0 complete when baseline dashboard shows publish success/failure rates per platform for 7 days.

Phase 1 — Additive schema (1 week)

Goal: Deploy new tables and mutations in shadow mode. No behavior change.

Tasks

  1. Create packages/database/convex/schemas/publish.ts (SSOT)
  2. Register publish_jobs, publish_attempts in schema.ts
  3. Add publishStatus, activeRunId to basePostSchema
  4. Implement convex/publish.ts: createPublishRun, completeAttempt, derivePostPublishStatus
  5. Wire createPublishRun in shadow mode — called after existing queue path, creates jobs but doesn't enqueue
  6. Backfill: none required (new fields are optional)

Feature flag

PUBLISH_PIPELINE_V2=shadow  // creates jobs but old path still executes
Gate

Shadow jobs created for 100% of publishes. Job count matches provider count. No user-visible change.

Phase 2 — Dual path (1 week)

Goal: Worker writes go through API AND old Convex path. Compare outcomes.

Tasks

  1. Deploy apps/api/src/routes/internal/publish.ts with HMAC auth
  2. Update SQS message shape to include publishJobId, attemptNumber
  3. Configure SQS DLQ with maxReceiveCount: 5
  4. Update packages/worker/client.ts to call /internal/publish/complete
  5. Update post.service.ts to call createPublishRun + enqueue with job IDs
  6. Keep updatePostPublishStatus as fallback (feature flag)
  7. Log discrepancies between old and new paths

Feature flag

PUBLISH_PIPELINE_V2=dual  // worker writes to API; old mutation still called for comparison
Gate

7 days of dual-path with <0.1% outcome discrepancy. All platforms tested. DLQ receives and processes test poison messages.

Phase 3 — Cutover (3 days)

Goal: Single write path. Derive post status from jobs. UI reads publishStatus.

Tasks

  1. Set PUBLISH_PIPELINE_V2=enabled
  2. Remove worker → updatePostPublishStatus calls
  3. Dashboard reads publishStatus instead of status for publish state
  4. Implement per-platform status chips (PARTIAL support)
  5. Wire dashboard retry button → POST /v1/posts/:id/retry
  6. Update publishScheduledPost to use createPublishRun + enqueue
  7. Deprecate updatePostPublishStatus (keep for 2 weeks, log callers)

UI migration

ComponentChange
dashboard-content.tsxFilter by publishStatus
failed-posts-alert.tsxShow PARTIAL + per-platform chips
use-post-actions.tsCall /v1/posts/:id/publish
post-creator.tsxDisplay publishStatus after submit
Gate

48 hours in production with zero P0 publish incidents. Retry flow tested on all platforms. Instagram automations verified.

Phase 4 — Webhooks (1 week)

Goal: Consolidate webhook routing through apps/api.

See 10 — Webhooks for full plan. Independent of publish pipeline — can slip if Phase 3 needs extra time.

Phase 5 — Cleanup (3 days)

Goal: Remove deprecated code and operational hardening.

  • Delete updatePostPublishStatus mutation
  • Remove dual-path logging and feature flags
  • Deploy stuck-job sweeper cron
  • Block new FREE plan signups (grandfather existing)
  • Remove hardcoded Lambda URL from post.service.ts → use SST Resource
  • Update CLAUDE.md and package docs
