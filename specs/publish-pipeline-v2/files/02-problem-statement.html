02 — Problem Statement

Why Delulu Social's publishing architecture is fragile and what user-visible failures result.

Symptoms

SymptomUser impactFrequency
Post marked FAILED after one platform succeeds User thinks entire post failed; successful platform post is hidden Common on multi-platform posts
Post stuck in PROCESSING Dashboard shows indefinite spinner; no retry affordance Intermittent
Duplicate publish on SQS redelivery Same content posted twice to a platform Rare but high severity
Transient API error → permanent failure Rate limits and 5xx errors not retried Common during platform outages
No per-platform status in UI User cannot see which of 3 targets succeeded Always (multi-platform)

Root causes

1. Worker writes post status directly

The Lambda worker calls api.posts.updatePostPublishStatus — a public Convex mutation — after each platform attempt. This mutation sets posts.status to either PUBLISHED or FAILED for the entire post, not per platform.

// packages/worker/client.ts (today)
await convex.mutation(api.posts.updatePostPublishStatus, {
  postId,
  status: "PUBLISHED", // or "FAILED" — overwrites whole post
  platformPostData: { ... },
});

When a post targets Instagram + Twitter + LinkedIn, the last worker to finish wins. If Instagram succeeds and Twitter fails, the post may show FAILED even though Instagram published.

2. No job-level state machine

There is no publish_jobs table. SQS messages carry only socialPublishInput and socialType — no job ID, no attempt number, no idempotency key. The system cannot answer:

  • How many platforms are still in flight?
  • Which attempt failed and why?
  • Should this message be retried or dead-lettered?

3. No retry or DLQ semantics

SQS messages are processed once. On failure the worker writes FAILED and returns — no exponential backoff, no maxReceiveCount, no dead-letter queue. Transient errors (rate limits, 5xx) are treated identically to permanent errors (invalid token, policy violation).

4. Fire-and-forget queueing

Both post.service.ts and publishScheduledPost loop over providers and POST to the Lambda trigger URL without tracking per-provider outcomes. If queueing itself fails mid-loop, some providers are enqueued and others are not — with no rollback.

5. Coupled side effects in one mutation

updatePostPublishStatus bundles status update, platform post embedding, streak tracking, automation linking, and video cleanup scheduling. Any partial failure or race in multi-provider publishes can leave inconsistent aggregates and automations.

6. No observability

There are no structured events for publish funnel stages. Debugging requires CloudWatch log spelunking across Lambda, Convex, and the dashboard with no correlation ID tying a post to its SQS messages.

Critical scenario

Multi-platform partial failure: User publishes to IG + X + LinkedIn. IG succeeds (worker writes PUBLISHED). X fails with rate limit (worker writes FAILED). LinkedIn still processing. Final state depends on message ordering — user sees inconsistent status, automations may not link, streak may or may not update.

What we are not fixing here

  • Provider API quirks (Instagram trial reels, TikTok creator info) — those stay in packages/worker/providers/
  • Convex as primary database — migration to SQL is explicitly deferred
  • Scheduling infrastructure (CallMeLater) — unchanged; only the publish execution layer is refactored

Success criteria (summary)

See 12 — Acceptance Criteria for full testable criteria. At a high level:

  • Multi-platform partial publish shows PARTIAL with per-platform chips
  • Transient errors retry automatically (up to 5 attempts)
  • Duplicate SQS delivery is idempotent (no double publish)
  • Dashboard retry button creates a new publish run for failed jobs only
  • Zero regression on Instagram automations and approval workflow
