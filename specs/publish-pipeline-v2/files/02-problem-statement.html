Hub / Problem Statement

Problem Statement

Publishing feels fragile because editorial and execution concerns are fused.

Core issue

Convex is the system of record. The ECS/SQS worker calls Convex mutations directly for publish status. Call Me Later webhooks hit Convex HTTP. Failed post retry is a TODO. The real-time dashboard depends on Convex subscriptions — all fine. The problem is that success and failure paths share one architecture with no job isolation.

Mixed status semantics

Today posts.status conflates:

  • Editorial: SAVED, SCHEDULED, DELETED
  • Execution: PROCESSING, PUBLISHED, FAILED

A scheduled draft and a failed publish both need different UX and query patterns but share one enum.

Acceptance criteria (target state)

  • A failed publish never corrupts post editorial state
  • Retries are automatic with max attempts + dead letter queue
  • Publish audit log per attempt
  • Migration runs with zero downtime

See 13 Acceptance Criteria for verification steps.

What this is NOT

This is not a mandate to change the database provider. Convex works well for real-time app state, automations, and approvals. The team wanted a cleaner architecture they can understand end-to-end — that means separating concerns, not swapping vendors.
