Instagram exception (ADR-005)

Instagram DM automations use multi-turn session state (automationSessions, automationMediaTriggers). The existing Lambda handler:

  • Short-circuits via automationMediaTriggers index
  • Manages button-tap session flows
  • Has been battle-tested in production

Decision: Instagram DM webhooks continue to hit the AWS Lambda directly. The apps/api/webhooks/instagram route acts as a proxy — verifying the Meta signature, then forwarding DM events to Lambda and handling non-DM events (media insights, mentions) locally.

Dual endpoint cutover

During Phase 4 migration, both old and new endpoints are active:

  1. Deploy apps/api/webhooks/* routes
  2. Register new URLs in platform developer consoles alongside existing ones
  3. Monitor for 48 hours — compare event counts
  4. Remove old Convex HTTP / Lambda URLs from platform consoles
  5. Deprecate old handlers (keep code for 2 weeks as fallback)

CallMeLater integration change

Currently: CallMeLater → convex/http.ts → publishScheduledPost

Target: CallMeLater → apps/api/webhooks/callmelater →

  1. Verify shared secret
  2. Call createPublishRun (creates jobs)
  3. Call /internal/publish/enqueue

This aligns scheduled publish with the same pipeline as publish-now (ADR-002).

Webhook handler requirements

  • Idempotent — platform webhooks may deliver duplicates; use event ID dedup
  • Fast ACK — return 200 within 5 seconds; defer processing to Convex action
  • Structured logging — log event type, platform, correlation ID
  • No direct DB writes — all mutations go through Convex (same as publish pipeline)

Out of scope for Phase 4

  • apps/web Outrank webhook — separate content pipeline, no change
  • New webhook providers — only migrate existing handlers
  • Cloudflare Workers — webhooks route through apps/api (existing deployment), not a new CF Worker service
Dependency

Webhook migration depends on Phase 3 cutover. Scheduled publish via CallMeLater should use createPublishRun — which only exists after Phase 1.
