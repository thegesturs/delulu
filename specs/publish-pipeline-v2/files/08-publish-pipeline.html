Publish Pipeline v2

State machine, retries, idempotency, and error taxonomy.

Job state machine

QUEUED ──► PROCESSING ──► PUBLISHED
                │
                ├──► FAILED (permanent error)
                └──► DEAD_LETTER (max transient retries exhausted)
StateMeaning
QUEUEDJob created; SQS message sent or scheduled
PROCESSINGWorker picked up; attempt STARTED logged
PUBLISHEDProvider returned platform post ID
FAILEDPermanent error — no auto-retry
DEAD_LETTERTransient retries exhausted — ops/manual retry

Post publishStatus derivation

Job states for post's active runpublishStatus
Any QUEUED or PROCESSINGIN_PROGRESS
All PUBLISHEDPUBLISHED
Mix PUBLISHED + FAILED/DEAD_LETTERPARTIAL
All FAILED or DEAD_LETTERFAILED
No active jobsIDLE

Legacy posts.status mapped for UI compat: PUBLISHED→PUBLISHED, PARTIAL→FAILED (or new PARTIAL), IN_PROGRESS→PROCESSING.

Idempotency

  • Job creation: idempotencyKey = ${runId}:${socialProviderId} — unique index prevents duplicate jobs per run
  • Attempt completion: completePublishAttempt(jobId, attemptNumber) — no-op if attemptNumber < job.attemptCount
  • SQS: message body includes publishJobId; FIFO optional with MessageDeduplicationId = jobId
  • Provider dedup: persist platformPostId on attempt before marking SUCCEEDED — retry must not double-post

Retry policy

Error classCodesAction
Transient NETWORK_ERROR, RATE_LIMIT_EXCEEDED, API_ERROR (5xx), MEDIA_PROCESSING_TIMEOUT Requeue with backoff; increment attemptCount
Permanent INVALID_ACCESS_TOKEN, NO_CONTENT, INVALID_MEDIA, PROFILE_NOT_FOUND, API_ERROR (4xx) Mark FAILED immediately; delete SQS message

Backoff: delay = min(retryAfter ?? 2^attempt × 60s, 3600s)

Max attempts: 5 → DEAD_LETTER

SQS: maxReceiveCount: 5 on redrive policy → DLQ

Worker must call isRetryableError() and attach errorClass + errorCode to completion payload.

Audit log flow

  1. Worker receives SQS message with publishJobId
  2. POST /internal/publish/heartbeat → job PROCESSING, attempt STARTED
  3. Call provider.publish()
  4. POST /internal/publish/complete → attempt SUCCEEDED or FAILED
  5. Convex derives post status + runs side effects (streak, linkPublishedPost, video cleanup)

Manual retry

publish.retryJob({ jobId }) or publish.retryPost({ postId }) creates a new runId and new jobs for failed/dead-letter providers only. Does not re-publish already-succeeded platforms unless user selects "retry all".

Stuck job sweeper

Convex cron (Phase 5): jobs in PROCESSING for > 15 minutes → reset to QUEUED or mark FAILED with reason WORKER_TIMEOUT.
