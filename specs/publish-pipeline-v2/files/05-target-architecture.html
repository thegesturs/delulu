Status separation

v2 splits post state into two orthogonal dimensions:

FieldScopeValuesWriter
posts.status Lifecycle / editorial SAVED, SCHEDULED, DELETED User actions, scheduler
posts.publishStatus Publish orchestration QUEUED, PROCESSING, PARTIAL, PUBLISHED, FAILED Derived from publish_jobs
publish_jobs.status Per-platform job QUEUED → PROCESSING → PUBLISHED | FAILED | DEAD_LETTER Pipeline mutations

Derive post publishStatus

function derivePostPublishStatus(jobs: PublishJob[]): PublishStatus {
  if (jobs.length === 0) return "QUEUED";
  if (jobs.every(j => j.status === "PUBLISHED")) return "PUBLISHED";
  if (jobs.every(j => j.status === "FAILED" || j.status === "DEAD_LETTER")) return "FAILED";
  if (jobs.some(j => j.status === "PUBLISHED") &&
      jobs.some(j => j.status === "FAILED" || j.status === "DEAD_LETTER")) return "PARTIAL";
  if (jobs.some(j => j.status === "PROCESSING")) return "PROCESSING";
  if (jobs.some(j => j.status === "QUEUED")) return "QUEUED";
  return "PROCESSING";
}

Idempotency model

  • Each publish_job has a unique _id included in SQS message as publishJobId
  • completeAttempt checks job status before transitioning — if already PUBLISHED, return success without re-publishing side effects
  • Attempt rows are keyed by (publishJobId, attemptNumber) — duplicate completions are no-ops
  • Side effects (streak, automation link, video cleanup) fire only on first transition to PUBLISHED

Retry model

  • SQS maxReceiveCount: 5 with dead-letter queue
  • Worker reports errorClass: TRANSIENT → job stays PROCESSING, SQS visibility timeout handles retry
  • Worker reports errorClass: PERMANENT → job → FAILED, message deleted from queue
  • After 5 receives → job → DEAD_LETTER, message in DLQ for manual inspection
  • Dashboard "Retry" creates new publish_run with fresh jobs for failed platforms only

Gateway pattern (apps/api)

Workers never call Convex mutations directly. All completion writes go through:

POST /internal/publish/complete
  Authorization: HMAC-SHA256(workerSecret, body)
  Body: {
    publishJobId, attemptNumber, status,
    platformPostId?, platformPostUrl?,
    errorCode?, errorClass?, errorMessage?
  }

The API validates HMAC, calls Convex completeAttempt, and returns structured errors. This centralizes auth, rate limiting, and logging.

Preserved

Convex remains system of record. Real-time subscriptions unchanged. Provider implementations in packages/worker/providers/ unchanged. Instagram automations and approval workflow untouched.

Phase 4 addition — Webhooks

After pipeline cutover, inbound platform webhooks route through apps/api/webhooks/* instead of scattered Lambda handlers. Instagram DM webhooks remain on AWS Lambda (see 10 — Webhooks).
