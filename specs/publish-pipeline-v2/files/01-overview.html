01 — Overview

Executive summary for Publish Pipeline v2: fix Delulu Social's fragile multi-platform publishing without migrating off Convex.

Status: Draft  ·  Effort: M (~3–4 weeks)

Recommendation

Keep Convex as system of record. Add publish_jobs and publish_attempts tables, derive post publish status from job aggregates, and route all worker completion writes through apps/api internal endpoints.

Goals

  • Reliable multi-platform publish — one job per post × provider, with explicit state and retries
  • Correct partial-failure semantics — post shows PARTIAL when some platforms succeed and others fail
  • Idempotent worker completion — duplicate SQS deliveries cannot corrupt post state
  • Observable pipeline — every attempt logged; PostHog events for funnel analysis
  • Zero-downtime migration — additive schema first, dual-write path, then cutover

Orchestration patterns

Mature publish systems converge on a small set of orchestration patterns. Delulu v2 adopts these without prescribing a specific external product:

Pattern

Job-per-target

One durable job record per post × social provider per publish run. Enables per-platform retries, status chips, and partial success.

Pattern

Derived aggregate status

Post-level publishStatus is computed from child jobs — never written directly by workers. Prevents race conditions on multi-provider posts.

Pattern

Attempt log

Append-only publish_attempts rows capture every try. Supports debugging, SLA metrics, and audit trails.

Pattern

Gateway writes

Workers call an authenticated internal API instead of public Convex mutations. Centralizes idempotency, validation, and side effects.

Pattern

Queue + DLQ

SQS with maxReceiveCount and dead-letter queue for poison messages. Transient errors retry with exponential backoff.

Pattern

Error taxonomy

Classify errors as TRANSIENT vs PERMANENT. Permanent errors skip retry; transient errors re-queue.
